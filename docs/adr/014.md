# ADR-014 — Bind Direct owner grants to Agent enforcement

Status: Proposed  
Date: 2026-09-22  
Issue: [DP-013](https://github.com/pareshnev-hub/dp-beget-bridge/issues/13)

## Context

DP-012 proved a live ChatGPT DCR and `files:read` flow, but its approval secret, DCR client ID, transactions and access tokens are staging-only. MCP currently hides tools according to the OAuth scopes, while the Agent authenticates a single broad `DP_AGENT_TOKEN` and does not know the OAuth owner, grant or scope. A caller able to reach the Agent with that token can exercise more capabilities than the current ChatGPT read-only grant. Session records likewise have no owner ID.

DP-006 already provides an operation ledger and DP-009 separates MCP, Agent and work identities. ADR-005 requires local Direct authorization; ADR-010 requires transactional local state. This decision specifies how DP-013 uses those boundaries without changing the working Secure MCP Tunnel.

## Proposed decision

1. **Local owner and client identity.** A one-time, expiring bootstrap performed through the VPS owner console creates one owner identity. Store only a digest of the bootstrap proof; consume it atomically. Persist the public OAuth client registration independently of the approval secret, so rotating owner credentials does not invalidate a registered ChatGPT client. A DCR client has exact redirect URIs and cannot request scopes outside the server policy.
2. **Durable grant record.** Use a versioned SQLite auth store owned by `dp-mcp`, distinct from the Agent's session/operation DB. Record owner ID, client ID, resource, approved scope set, execution profile, consent time, expiry and status. Keep bearer material out of plaintext storage. Bind an authorization code and an access token to one existing grant; rejection or state failure cannot create an implicit grant.
3. **Human consent.** Approval is a browser/owner action bound to an expiring transaction, exact client, resource, redirect, scope set and CSRF state. The owner sees the effective UNIX identity and an explicit disclosure that `terminal:execute` can read and change files allowed to that identity, regardless of separate file-tool scopes. No MCP argument, model response, terminal output or `confirmed=true` value can expand consent. Full shell and unattended rights require a separate explicit grant profile; DP-012 read-only consent never upgrades itself.
4. **Enforce at Agent.** MCP tool filtering remains a convenience, not the authorization boundary. Separate the OAuth and legacy tunnel service principals with distinct local credentials or verified IPC identities **before** making OAuth grant context mandatory; they currently share one Agent bearer, so Agent cannot safely infer the caller from a client-supplied flag. Every OAuth MCP-to-Agent capability call carries a bounded authenticated authorization context constructed by MCP from the validated grant. Agent rejects missing, expired, malformed or insufficient context **before** opening a session, reading data or changing state. It maps method/path to the required capability itself and ignores scope copied from a model-controlled body. Bind context to the authenticated service principal, audience, expiry and request against replay. Preserve the existing tunnel principal under its separately defined compatibility policy while migrating it; if principals cannot be distinguished, fail closed on the new OAuth path and leave the working tunnel unchanged.
5. **Session ownership.** Newly created sessions and operations record owner ID on the Agent side. Session reads, writes, close and purge require the same owner or a separately approved administrative migration. Pre-existing sessions without an owner remain unavailable through the new OAuth path until the VPS owner explicitly adopts them locally. They are never deleted or silently claimed during migration.
6. **Failure and restart.** Missing/incompatible/corrupt auth state blocks new grants and MCP calls, while already running Session Host jobs continue. Migration creates a verified backup and fails closed if interrupted. A revoke ends future authorization; stopping an already running command is a separate owner action. Refresh rotation and reuse detection are DP-014, so no persistent unattended grant should be marketed until that lifecycle is implemented.

## Implementation slices

- **M002a:** versioned owner/client/grant store with migration backup, one-use bootstrap and data-access tests; no production activation.
- **M002b:** owner consent page, exact transaction binding and grant issuance; keep scope `files:read` in initial staging.
- **M002c:** split OAuth and tunnel service principals; add Agent authorization context and policy mapping, owner ID on new sessions, legacy-session migration gate and end-to-end read-only tests. Verify existing tunnel calls still work without broader rights.
- **M002d:** explicit restricted shell profile consent and negative tests, then staged terminal tests. DP-014 implements refresh, revoke family and re-pair.

Each slice uses a separate reviewable PR. Do not switch the main Secure MCP Tunnel or enable broader OAuth scopes while an enforcement slice is incomplete.

## Acceptance evidence

Test one-use/expired bootstrap, CSRF/replay, wrong client/redirect/resource, scope escalation, grant expiry, forged Agent context, request replay, denied cross-owner session access and a legacy unowned session. Restart both services around a live operation; confirm it continues without creating a new grant. A real ChatGPT client must prove read-only and later explicit restricted-shell flows against the exact deployed revision. Tests and logs must never include live secrets, bearer tokens, command bodies or file contents.

## Trade-offs

Two local SQLite stores preserve the existing UID boundary and prevent the work identity from reading auth state, but require coordinated owner checks at MCP and Agent. The Agent will trust the authenticated MCP service to present a valid bounded context; this is an explicit service trust boundary, not authorization supplied by a model. Multi-owner shared-UID isolation, organization RBAC and refresh-family logic are outside this ADR.
