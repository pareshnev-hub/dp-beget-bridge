# ADR-015 — Rotate, revoke, reset and re-pair Direct credentials

Status: Proposed  
Date: 2026-09-22  
Issue: [DP-014](https://github.com/pareshnev-hub/dp-beget-bridge/issues/14)

## Context

DP-013 binds a short-lived access token to a durable owner grant and enforces a signed owner/grant/scope context at the Agent. Access tokens are currently process-local and the authorization server supports only the authorization-code grant. A service restart therefore requires a new owner approval, while there is no durable refresh-family, revocation or owner reset lifecycle.

R0003 requires unattended but bounded access, immediate denial of new work after revocation, deterministic refresh reuse handling and a re-pair flow that does not delete terminal transcripts.

## Decision

1. **Durable refresh families.** Auth schema v2 stores a token family bound to one owner, client, resource and authorization grant. Refresh tokens are random opaque values; only a domain-separated SHA-256 digest is stored. Families and tokens have absolute expiry and explicit status.
2. **Atomic rotation.** A refresh exchange runs in one SQLite `BEGIN IMMEDIATE` transaction. It consumes exactly one active generation and installs exactly one successor. The access token is issued only after the durable rotation commits.
3. **Reuse policy.** Reuse of a consumed refresh token marks the complete family `COMPROMISED` and revokes every still-active refresh generation in that family. Access-token authentication checks current family status, so an access token from the losing or previously successful concurrent exchange is no longer accepted.
4. **Concurrent refresh semantics.** For two exchanges using the same refresh token, one may rotate first; the second deterministically triggers the reuse policy. The final state is a compromised family with no valid refresh chain. The server never attempts a grace-window replay that could create two valid branches.
5. **Revocation.** Revoking a grant transactionally marks the grant and its token families revoked. New MCP calls fail authorization. Already-running Session Host processes are not terminated: stopping a process remains a separate explicit owner action.
6. **Reset and re-pair.** Local owner reset revokes all grants and token families, disables registered clients and replaces the one-use bootstrap proof. It changes only the private auth store. Agent session state, tmux processes and transcript files are retained unless the owner separately invokes their existing explicit close/purge operations.
7. **Fail closed.** OAuth token exchange and request authentication fail when auth state is missing, corrupt, locked, newer than supported or cannot be committed. No in-memory fallback can mint a durable token chain.
8. **No secret observability.** Access tokens, refresh tokens, authorization codes, approval/bootstrap proofs and their digests are excluded from logs, diagnostics, telemetry and owner status output. Status exposes identifiers, states, expiry and the already-running-task policy only.
9. **Rollback fence.** Revocation also updates the existing grant/client status understood by schema v1. A downgrade cannot make a revoked grant active. If schema compatibility is uncertain, services stop and require re-pair rather than reconstructing credentials.

## Protocol behavior

- Authorization metadata advertises `authorization_code` and `refresh_token`, plus a revocation endpoint.
- Authorization-code exchange creates the first refresh generation and returns one access token plus one refresh token.
- Refresh exchange requires exact client and resource binding and cannot expand scopes or execution profile.
- The revocation endpoint is idempotent and does not reveal whether a token existed.
- Reset is local-owner administration, not an MCP/model tool.

## Implementation slices

- **M003a:** auth schema v2, migration backup/recovery, token-family primitives, grant revoke and owner reset.
- **M003b:** refresh-token protocol, atomic rotation/reuse detection, revocation endpoint and access-family checks.
- **M003c:** owner administration command, sanitized status/policy output, installer configuration, live revoke/reset/re-pair evidence.

## Acceptance evidence

- AUTH-05 revoked grant rejects new requests while a pre-existing Session Host task is not implicitly stopped.
- AUTH-06 reused old refresh token compromises its family and cannot create a new valid chain.
- AUTH-07 two refreshes of one generation produce the documented deterministic final state.
- AUTH-10 reset rotates credential state and permits re-pair while a transcript sentinel remains intact.
- Forced auth-store failure rejects refresh and request authentication without token material in logs.
