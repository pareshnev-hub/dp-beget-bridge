# DP Beget Bridge — Architecture & Security Audit

Date: 2026-09-21  
Repository: `pareshnev-hub/dp-beget-bridge`  
Baseline: `f22032ec6c465f0eeffec6c360959d266941ea29`

## Executive verdict

The project has a sound product direction and does not need a rewrite. The current implementation is a technical preview rather than a safe public connector.

The correct path is:

1. harden file/session/runtime safety;
2. prove real tmux/systemd persistence;
3. complete local Direct OAuth/consent/revoke;
4. build reproducible install/update/rollback;
5. harden large transfers;
6. only then build a Catalog Relay if current distribution requirements justify it.

The key correction to the earlier generic architecture prompt is that this project is a **Linux VPS MCP bridge**, not a Windows remote-control agent.

This green CI does not prove the most important runtime property: a real long-running terminal process surviving relevant MCP/Agent restarts on a Linux/systemd host.

## What is already correct

### Product principles
- Direct traffic goes from client to the user's VPS.
- The DP site is not intended to be in the execution path.
- Terminal sessions are backed by tmux.
- MCP request timeout is intended to stop waiting, not kill the underlying process.
- Terminal continuity output is local.
- Telemetry is opt-in.
- Agent is loopback-only by default.
- MCP and Agent use separate bearer tokens in the preview.
- File paths are restricted through an allowed-root policy.
- Download links use random short-lived opaque grants.
- Logs are structured and already redact obvious secret-key fields.
- Repository already has release/security/privacy scaffolding.

## Detailed critical findings

### F01 — destructive move pre-delete — P0

Current move logic may remove an existing destination before the move itself is known to succeed.

Risk cases include:
- source equals destination;
- source is missing while destination exists;
- rename fails after destination deletion;
- complex cross-device fallback.

Required behavior:
- never delete destination before a successful replacement commit;
- explicit same-path no-op/error;
- atomic no-replace for `overwrite=false`;
- unsupported response for cases not yet safely implemented;
- regression tests before re-enabling broad replacement behavior.

This is the first implementation issue.

### F02 — root-by-default possibility — P1

The installer derives the service user from `SUDO_USER` and can fall back to root.

Target:
- no root as an implicit normal runtime identity;
- explicit owner/work identity;
- separate service credentials;
- admin/root execution only as an explicit profile with disclosure.

### F03 — external attachment fetch / SSRF — P1

The MCP layer fetches a provided download URL.

Required controls:
- HTTPS/contract source policy;
- DNS + resolved-address checks;
- IPv4/IPv6 private/loopback/link-local rejection as appropriate;
- redirect validation on every hop;
- bounded size;
- timeout;
- bounded concurrency;
- cancel on downstream disconnect;
- never forward Agent bearer credentials to source origin.

Do not use an unrestricted fetch fallback if policy validation fails.

### F04 — file input contract/descriptors — P1

The declared MCP file schema and actual target-client contract must be tested together.

Required:
- contract snapshot tests;
- optional filename fallback behavior;
- required file identity/reference fields according to actual client contract;
- correct read-only/destructive annotations;
- schema/structured-content consistency.

### F05/F06 — command marker is not authoritative completion — P1

The preview wraps commands with a completion marker and looks for that marker in captured PTY output.

Problems:
- shell echo may expose the marker text before the command truly finishes;
- untrusted output can forge marker-like content;
- a fixed first output window can miss a late completion after large output;
- interactive/exec/exit cases do not always map cleanly to a shell exit code.

Target:
- Operation object separate from Session;
- managed completion/status channel independent of PTY transcript;
- honest `UNKNOWN` when the system cannot safely know the result.

### F07 — command concurrency/idempotency — P1

Multiple write operations can target one terminal without a durable single-writer model.

Target:
- operation ID assigned before execution;
- caller idempotency key + request fingerprint;
- one writer per session;
- duplicate same-key/same-payload returns existing operation;
- same-key/different-payload is conflict;
- crash ambiguity does not trigger automatic replay.

### F08 — retained output must remain addressable — P1

Retaining terminal output while removing the metadata required to locate/read it makes `keepOutput` semantically inconsistent.

Target:
- preserve CLOSED session metadata;
- archive and purge are separate operations;
- retained transcript remains readable after API restart.

### F09 — transfer backpressure/cancellation — P1

Streaming must remain bounded across every hop.

Required:
- use pipeline/equivalent bounded flow control;
- stop upstream work when client disconnects;
- per-transfer and aggregate limits;
- inactivity deadlines;
- memory-budget tests with a slow reader.

### F10 — filesystem race boundaries — P1

Lexical + realpath validation is useful but not a complete defense against filesystem mutations occurring between validation and use.

Target:
- safe mutation primitives;
- roots protected from move/delete;
- explicit symlink policy;
- reject dangerous ancestor/descendant overlaps;
- temporarily disable recursive/complex operations that cannot be proven safe.

### F11 — execution/service secrets — P1

A shell running under an identity that can read the same service configuration can potentially access internal credentials even if those values were removed from its environment.

Target:
- separate UNIX identities/ACLs;
- separate secrets storage;
- clean minimal execution environment;
- work identity unable to read auth/token stores in restricted mode.

### F12 — tmux/systemd lifecycle proof — P1

The systemd unit currently expresses an intent for tmux sessions to survive API restart, but this must be demonstrated on a real/disposable Linux host.

Required scenarios:
- start long-running command;
- stop waiting;
- restart MCP;
- restart Agent;
- read continued output;
- send interactive input;
- explicitly close only the intended session.

Do not mark this complete based on unit tests alone.

### F13 — resource exhaustion — P1

A persistent terminal with large output can exhaust disk/memory without explicit ceilings.

Target:
- max active sessions;
- transcript budget;
- free-space reserve;
- output-rate/buffer limits;
- transfer concurrency;
- explicit degraded/gap behavior.

Do not silently kill user processes solely because transcript storage is full.

### F14 — logging token leakage — P1

Key-name redaction does not sanitize secrets embedded inside URL paths or exception strings.

Target:
- route templates in request logs;
- field allowlist;
- error sanitizer;
- canary-secret tests through error paths;
- proxy access-log review;
- safe diagnostic export.

### F15/F16 — telemetry semantics/recovery — P2

The central statistics path must:
- recover after individual storage failures;
- persist/deduplicate daily activity correctly;
- run retention without requiring restart;
- treat meaningful terminal/file action as active usage;
- never label service starts as exact human DAU.

Telemetry remains disabled until this is corrected/deployed.

## Threat-model conclusions

### Token or MCP URL compromise
Mitigate with OAuth access-token lifetime, refresh rotation, revocation, audience/resource binding, rate limits and explicit grants.

### Prompt injection
Terminal/file content may contain adversarial instructions. It cannot modify scopes, grants or owner consent. Tool output is data.

### Destructive shell access
A full shell is inherently powerful. Keyword blocklists are not a security boundary. Use explicit execution profiles and owner grants.

### Path traversal/symlink/TOCTOU
Allowed-root checking is necessary but not sufficient. Mutation primitives and OS permissions remain part of the boundary.

### Disk exhaustion/fork/output abuse
Bound sessions/transfers/output and reserve disk. Consider process/resource controls for restricted profiles.

### Malicious update/supply chain
Public release requires immutable artifacts, checksums/signatures, dependency pinning, staged updates and rollback.

### Compromised Relay
Catalog Relay must not persist data-plane bodies. If TLS terminates there, Relay can see transit plaintext; document this honestly.

### Multi-tenant leak
Before Catalog pilot, test two owners with intentionally similar labels/session names and prove deny-by-default routing.

## Product answers

### Can Direct be autonomous?
Yes. Auth/grants/session/file state can live on the user's VPS. Website/telemetry/feedback/Relay are unnecessary for an already-installed Direct runtime.

### Can Direct work when pareshnev.com is down?
Yes, provided OAuth/authorization is local to the user's VPS origin and no runtime permission heartbeat is introduced.

### Does the user need a custom domain?
Not necessarily a separately purchased domain, but a stable HTTPS hostname is operationally useful for Direct. Installation should support coexistence with an existing reverse proxy.

### Can VPS migration avoid ChatGPT reconfiguration?
If the stable hostname remains the same, endpoint configuration can remain stable. Credentials may still require revoke/re-pair depending on migration policy.

### Is a Relay required immediately?
No. Build Direct first. Re-check the current distribution/catalog model before committing to a custom Relay.

### How should active users be counted?
Only among telemetry-enabled installations, based on meaningful terminal/file activity. Installation IDs are not people.

## Accepted technical debt

### TD-001 — Linux-first only
Reason: shortest path to a correct Beget VPS product.  
Review trigger: demonstrated demand for another OS.

### TD-002 — single-owner Direct model
Reason: avoids pretending one UNIX account is a multi-tenant security boundary.  
Review trigger: organization/multi-user product requirement.

### TD-003 — unsupported complex file mutations
Reason: returning unsupported is safer than shipping a lossy/racy fallback.  
Review trigger: journaled implementation + chaos/security tests.

### TD-004 — one-node Catalog pilot
Reason: HA infrastructure before real load is overengineering.  
Review trigger: measured reliability/load requirement.

## Overengineering to avoid now

Do not add before needed:
- Kubernetes;
- global multi-region;
- enterprise SSO;
- billing;
- durable central command/output bus;
- Postgres/Redis on each Direct VPS;
- microservices solely for organizational neatness;
- custom Relay before the distribution feasibility gate.

## Audit limitations

This audit reviewed repository code and project requirements around the baseline commit. It did not itself prove:
- behavior on the user's production Beget VPS;
- real ChatGPT/Codex OAuth integration;
- end-to-end network/TLS behavior;
- a third-party independent penetration test.

Those items are release acceptance tests, not assumed facts.
